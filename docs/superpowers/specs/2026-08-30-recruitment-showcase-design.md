# 招聘展示层设计

日期：2026-08-30
状态：已批准，待实施

## 目标

把仓库从“工程人员可以核查的项目”整理为“招聘者能在 3–5 分钟内理解、技术面试官能继续深入核查的嵌入式作品集”。展示主轴面向嵌入式固件与 RTOS 岗位，同时完整保留数据采集、存储恢复、通信协议、桌面端、TinyML、Bootloader/OTA 和可靠性证据等亮点。

展示层只重组已经存在且可追溯的事实，不改变固件、协议、硬件配置或发布状态，也不创造未经验证的性能、可靠性和模型泛化结论。

## 目标读者与阅读路径

### 第一层：招聘者，3–5 分钟

README 首屏应直接回答：

- 项目解决什么问题；
- 使用了哪些关键技术；
- 从传感器到桌面端是否形成实板闭环；
- 哪些结果已经验证；
- 项目体现了哪些嵌入式工程能力。

### 第二层：技术面试官，10–20 分钟

通过架构、数据链路、关键设计取舍、可靠性策略和证据入口继续核查：

- DMA、Cache、固定内存池和任务边界；
- 事件触发、EV03 持久化和 EL01 恢复；
- UART3/TERP 分块下载、CRC 与会话状态；
- AI 推理、模型生命周期和结果 sidecar；
- Bootloader、OTA、回退和发布门禁；
- Reliability Evidence 默认关闭、故障注入隔离和未完成的实板边界。

### 第三层：项目维护者

保留到源码、发布说明、公开证据包和学习材料的稳定链接，使 README 不承担全部细节。

## 信息架构

README 按以下顺序组织：

1. **项目标题与英文摘要**：一段简短英文摘要，随后是中文定位；不维护双份完整 README。
2. **一屏关键事实**：STM32H743、RT-Thread、ICM45686、2400-sample EV03、W25Q64、UART3/TERP、PySide6、TinyML、Bootloader/OTA、实板闭环。
3. **系统主链**：使用 GitHub 原生 Mermaid，从 IMU/FIFO/DMA 贯穿到事件、存储、通信、桌面端和 AI。
4. **工程亮点**：按实时采集、确定性内存、可靠存储、协议与桌面端、TinyML、升级与发布安全分组。
5. **可靠性增强**：区分“已实现的软件机制”“已取得的补充实板证据”“仍锁定的正式 Reliability-enabled Release”。
6. **真实运行结果**：使用仓库现有的五张桌面端事件回放图，选择信息互补的代表图组成紧凑画廊；不使用 AI 生成实板图。
7. **验证与证据**：展示自动化测试、Release gate、构建资源占用和公开证据入口，并说明验证范围。
8. **快速复现**：保留最短的环境自检、测试和 Release gate 命令；复杂操作链接到现有文档。
9. **仓库导航**：用表格解释 `firmware/`、`host/`、`ai/`、`protocol/`、`scripts/`、`evidence/`、`docs/`。
10. **版本和诚实边界**：明确 `v1.0.0` 是发布基线；当前 `main` 是 Reliability 默认关闭的后续开发基线；不称 V2.0。
11. **深入阅读**：链接发布说明、证据包、可靠性收口报告和[项目主链图谱（project main-chain atlas）](../../learning/project-chain-atlas.md)；本地面试学习总纲不纳入本次展示，待单独审查并提交后再考虑加入。

## 视觉与文案原则

- 采用工程证据型风格，避免竞赛式口号和无法复核的百分比。
- 中文为主体，顶部英文摘要只承担国际读者的快速理解。
- 使用 Markdown、表格、折叠块和 Mermaid，不引入网站框架或运行时依赖。
- 不依赖外部动态徽章作为核心信息源；即使第三方服务不可用，README 仍完整可读。
- 首屏不堆砌全部测试细节；数字必须带语境，例如“10/13 测试集准确率”不得写成泛化准确率。
- 每个主要能力尽量链接到一个稳定的源码目录、设计文档或证据入口。
- 图片使用相对路径和有意义的替代文本，避免绝对本机路径。

## 事实分级与发布口径

所有展示声明分为三类：

| 级别 | 可用措辞 | 约束 |
|---|---|---|
| 已发布并验证 | “V1 已实现并通过实板闭环” | 必须能追溯到 `v1.0.0` 发布说明和公开证据包 |
| 已实现、默认关闭 | “当前主线已实现可靠性增强，正式启用发布仍锁定” | 不得写成 V1 已包含或正式产品能力 |
| 未完成或未声明 | “未宣称”“仍需实板门禁” | 不得用 native、模拟或补充操作记录替代正式硬件结论 |

明确保留以下边界：

- 四分类模型测试集为 10/13、macro-F1 0.755952，不外推为独立 session 泛化性能；
- 不宣称已完成 72 小时长稳、100 次物理掉电或工业量产级认证；
- UART3 重连和冷启动记录属于有价值的补充证据，但不解锁当前 revision 的 Reliability-enabled Release；
- `v1.0.0` 标签和发布产物保持唯一正式回退基线。

## 文件边界

第一轮实施修改范围：

- 重写根目录 `README.md`；
- 新增 `docs/showcase/architecture.md`，承载详细架构、任务边界和关键取舍；
- 新增 `docs/showcase/recruiter-walkthrough.md`，提供 3 分钟、10 分钟和深度核查路线；
- 复用 `evidence/releases/v1.0.0/desktop/` 中已有图片，不复制原始证据；
- 必要时为现有文档补充少量稳定交叉链接。

第一轮不包含：

- 修改固件、Host、AI、协议或构建逻辑；
- 创建网站、在线演示服务、视频或 AI 生成硬件图；
- 修改 Release、创建新版本标签或解锁 Reliability-enabled 构建；
- 把本地主目录中未提交的个人学习材料自动公开。

## 验证

展示层完成后执行最小而充分的检查：

1. 扫描所有新增或修改 Markdown 中的相对链接，确认目标存在；
2. 检查图片路径、文件名大小写和替代文本；
3. 检查 Mermaid 节点语法和 GitHub 可渲染结构；
4. 搜索 `TBD`、`TODO`、绝对本机路径和禁止性夸大措辞；
5. 对照 V1 release notes、公开证据包和 Reliability closeout 逐项核验数字与状态；
6. 运行 `git diff --check`；
7. 运行 V1 兼容性契约测试，确认文档工作未带入代码回退。

## 完成标准

- 新读者在 README 首屏能识别项目目标、硬件平台、软件架构和实板状态；
- 主链图可以从采集一直追踪到持久化、下载、回放和 AI；
- 已验证、实验性和未声明能力不混写；
- 所有关键数字和图片都有仓库内来源；
- README 不依赖私人本机文件，也不暴露本机绝对路径；
- `main`、`v1.0.0` 和 Reliability-enabled Release 的关系表述一致；
- 文档检查和 V1 兼容性测试通过。
