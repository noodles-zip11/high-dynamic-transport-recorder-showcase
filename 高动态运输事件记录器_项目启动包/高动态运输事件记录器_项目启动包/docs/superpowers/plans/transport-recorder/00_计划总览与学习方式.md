# 高动态运输事件记录器：计划总览与学习方式 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 用多份可独立验收的学习型计划，完成可靠运输事件记录器，并确保开发者能够亲手配置、验证和解释关键技术。

**Architecture:** 总计划只保存顺序、依赖和阶段门槛；每个子系统拥有独立MD，包含学习目标、手动步骤、文件、代码、测试、预期结果和常见错误。当前采用“软件先行、采购延后”的双阶段路线：先在CLion和本机测试中完成可独立验证的软件基础，再购买硬件进入板级阶段。

**Tech Stack:** CLion、STM32H743VIT6、RT-Thread Standard、C11、STM32CubeH7、CMSIS-DSP、STM32Cube.AI、SCons、GCC、Python 3.12、PySide6、PyQtGraph、pytest。

**Repository rule:** 未经用户明确授权，不创建提交、推送、PR、Release或部署。

## 0. 开发前分支与Worktree门禁

执行任何子计划前，先阅读仓库根目录的[AGENTS.md](../../../../../../AGENTS.md)和[版本管理工作流决策](../../../../../../docs/decisions/version-control-workflow.md)。每个可审查的软件增量从最新`main`创建一个专用分支与工作树；`main`只保存通过软件门禁的集成基线，不直接开发。

```powershell
git rev-parse --is-inside-work-tree
git status --short
git worktree add ..\高动态运输事件记录器-worktrees\<slug> -b feature/<slug> main
Set-Location ..\高动态运输事件记录器-worktrees\<slug>
git branch --show-current
git status --short
```

只有第一条输出`true`、当前分支与任务名称一致且两次状态检查均无输出时，才允许修改文件。若Git无效、`main`不存在、目录或分支已存在，立即停止并先运行`git worktree list`排查；不得靠删除、硬重置或切回`main`绕过。完成软件测试、构建和审查后，将该任务分支经授权合入`main`；硬件尚未验证必须记录为未验证项，而不是长期阻塞软件集成。

## 1. 为什么要拆成多份

这个项目至少包含六个相对独立的问题：实时采集、可靠存储、上位机、AI、OTA和CAN。把所有步骤塞进一个文件会产生三个问题：

- 读者不知道当前应该只学哪一部分；
- 后期硬件实测结果会让早期写死的参数失效；
- 验收失败时很难定位应该退回哪个阶段。

因此每份MD都必须产生一个可以单独演示和测试的结果，不把“看过文档”当作完成。

## 2. 当前执行策略：先软件，后采购

硬件采购目前明确延后。延后期间不空等，也不凭参考板参数编造硬件结果，而是完成以下软件工作：

1. 先执行[02_Windows开发环境与工程骨架.md](02_Windows开发环境与工程骨架.md)，把CLion、GNU Arm工具链、SCons、Python和命令行脚本配通；
2. 再执行[00A_延后采购期间的软件先行计划.md](00A_延后采购期间的软件先行计划.md)，完成可在PC运行的C算法、假Flash、TERP解析器、Python工具和GUI样例；
3. [01_硬件采购与到货验收.md](01_硬件采购与到货验收.md)当前只做选型资料归档和预算表，不下单；
4. 每个软件阶段通过本机测试和构建门禁后，作为独立增量合入`main`；准备进入BSP和传感器验证时，再下单H743与ICM-42688-P；
5. 硬件到货后，从最新`main`创建专用硬件验证分支，按03及后续阶段的板级验收项测试、归档证据，并把必要修复合回`main`。

软件先行阶段不能替代实板验证。时钟、DMA、Cache、SPI波形、USB枚举、功耗和掉电恢复最终仍以实物测试为准。

## 4. 学习型执行循环

每个外设或算法都按以下六步执行：

1. 从数据手册找到寄存器、时序和限制；
2. 用自己的话写一页设计笔记；
3. 先写会失败的测试或可观察验收；
4. 手敲最小实现；
5. 用串口、逻辑分析仪、Map文件或测试脚本验证；
6. 关闭资料，用自己的话回答本文件末尾的问题。

不能只复制厂商例程后看到LED亮就算掌握。

## 5. 哪些内容建议手敲

必须亲手编写和解释：

- 外设初始化后的寄存器读回检查；
- ICM FIFO解析、DMA缓冲区和Cache一致性处理；
- 固定块内存池、环形预触发缓存和事件状态机；
- 日志头、CRC、提交标志和启动扫描；
- TERP帧解析、长度检查、重同步和分块重传；
- Bootloader状态机、试运行确认和回滚；
- 数据集切分、规则基线、模型评估和资源测量；
- 故障注入脚本与验收报告。

可以使用生成器或厂商库，但必须阅读结果：

- CMSIS启动文件和芯片头文件；
- STM32 HAL/LL库；
- CubeMX生成的时钟与引脚初始化初稿；
- RT-Thread官方BSP骨架；
- STM32Cube.AI生成的推理代码；
- PySide6 Designer生成的纯界面文件。

不建议手写CMSIS启动汇编、HAL库或神经网络算子；这些工作量大，却不能直接证明项目能力。

## 8. 时间、采购触发点和优先级

完整项目预计62～94个专注工作日，兼职约4～6个月。若时间不足，保留顺序为：

```text
可靠采集与存储

→ OTA回滚
→ 上位机完成度
```
