# Feature Implementation Plan

> **For the implementing agent:** Phase 07 code must not start until the user confirms this document. This document defines module ownership, dependency direction, data contracts, format compatibility, and acceptance boundaries.

**Goal:** Add SHT4x environment sensing, valid RTC time, health supervision, reset/power reporting, watchdog policy, and immutable event context with the smallest change to the existing architecture. Reed-switch/door sensing is deferred.

**Architecture:** Hardware drivers own transactions only. Services turn driver results into stable status. Health produces a copied `health_snapshot_t`. Event assembly takes one read-only snapshot at trigger time and serializes an event payload. The existing runtime-injected event-to-storage sink remains in place. EL01 keeps its event-header validation and recovery protection. Runtime is the composition root only.

**Tech Stack:** STM32H743, RT-Thread, STM32 HAL I2C/RTC/IWDG, SHT4x over I2C1, existing SPI NOR EL01 storage, C native tests, SCons, Python host decoder tests.

## 1. Scope and non-goals

### 1.1 Included in Phase 07

- SHT4x I2C acquisition and a one-second environment service.
- RTC UTC validity, backup-domain marker, and `time` MSH commands.
- Reset-cause capture, power-status representation, and watchdog policy boundary.
- Once-per-second health calculation, progress heartbeats, and a copied `health_snapshot_t`.
- EV02 event payload with an explicit recovery-validation branch, while preserving EV01 records and EL01 recovery guarantees.

### 1.2 Explicitly deferred

- Reed switch selection, wiring, GPIO/EXTI, debounce, door-state machine, and door event fields.
- PVD/BOR option-byte changes, shutdown writes, or any Flash operation in an interrupt.
- NTP/GNSS synchronization, time-calibration persistence, and persistent time-adjustment audit logs.
- A new storage thread or queue. Storage is synchronous until measured workload requires otherwise.
- RT-Thread private stack scanning. Stack-watermark fields are unavailable/zero in this phase.

## 2. Architecture rules

### 2.1 Allowed dependency direction

```text
                 app/runtime  (composition only)
                         |
       +-----------------+------------------+
       |                 |                  |
 app/health        app/event           app/diagnostics
       |                 |                  |
 app/services: time, environment, reset-power, storage
                         |
              components: event_log / drivers
                         |
                 bsp: pins, HAL, board
```

The arrows are dependency direction, not necessarily function-call direction. A lower layer must never include, call, or implement a type owned by a higher layer.

### 2.2 Non-negotiable rules

1. BSP, drivers, and components never include `firmware/app/` headers.
2. A service exposes its own status/snapshot API and does not know its consumers.
3. `health_service` reads provider status; it does not start hardware, write storage, or export events.
4. `event_service` may perform one read-only copy through the public health API when a trigger is accepted; it does not start, configure, or control health/time/storage services.
5. The existing `event_export_sink_t` callback injection remains in Phase 07. Its header ownership is a minor P3 issue, not a functional coupling or a 07 refactor target.
6. `event_log` continues to validate EL01 metadata, commit state, bounds, EV01/EV02 event header fields, and payload CRC during recovery. This integrity check is intentional.
7. `app_runtime` creates tasks and connects interfaces but contains no sensor, protocol, or health policy.
8. ISRs capture only minimal facts. They do not wait, log, allocate, serialize events, or write Flash.

## 3. Module ownership

| Module | Its only responsibility | Allowed dependencies | Forbidden dependencies |
| --- | --- | --- | --- |
| BSP | Pins, clocks, HAL setup, raw reset flags | HAL, RT-Thread | app, codecs, health policy |
| SHT4x driver | I2C command, delay, CRC, raw conversion | BSP I2C transport | service/event/health |
| Environment service | 1 Hz cache, age, validity, error counters | SHT4x driver, monotonic clock | health/event/storage |
| Time service | RTC read/set/invalidate and UTC validity | RTC/backup BSP, monotonic clock | health/event/SHT4x |
| Reset-power service | Capture/clear reset cause; power status | BSP reset/PVD interface | event/health policy |
| Storage service | Mount storage; provide the existing injected event sink/status | event log, NOR, event sink type | event logic/codec calls |
| `event_log` component | EL01 atomic recovery, EV01/EV02 header validation, CRC, erase/write | NOR driver | event state machine, health/service policy |
| Health service | Heartbeats, health state, copied snapshot | public provider APIs | HAL, event codec |
| Event service | Triggering, sample ownership, EV02 serialization; one snapshot copy at trigger | sample pool, public health snapshot, existing sink | storage implementation, hardware control |
| Runtime | Startup sequence and interface wiring | public module APIs | module internals/policy |
| Diagnostics | Format copied public data for MSH/UART | public snapshots | hardware control |

## 4. Existing event-storage boundary: retain in Phase 07

The current relation is already functionally one-way at runtime:

```text
event_service owns event_export_sink_t
        ^
        | callback value is injected by app_runtime
storage_service implements the callbacks
```

`event_service.c` does not include or call `storage_service`; it only invokes the injected callbacks. `storage_service.h` includes `event_service.h` only to name this callback type. That header placement is a small P3 architectural imperfection, not a runtime bottom-to-top call.

Phase 07 deliberately does **not** introduce `record_sink_t`, `system_context_t`, a new `app/contracts/` directory, or a broad interface refactor. Moving `event_export_sink_t` to a neutral header is a safe later cleanup if it is ever needed, but it gives no Phase 07 functional benefit and must not delay sensor/time/health work.

## 5. Startup and tasks

Runtime startup order is fixed:

1. Capture and clear raw reset flags before other initialization changes them.
2. Start time service and determine UTC validity; never fabricate a calendar date.
3. Mount EL01 storage and obtain the existing injected event-export sink.
4. Start existing IMU acquisition and event service with that sink.
5. Start the SHT4x environment service.
6. Start health supervision after providers publish initial `STARTING` status.
7. Enable physical IWDG only in a later, explicitly board-validated configuration.

Task ownership stays with its module. Phase 07 adds only an `environment` worker (1 Hz) and a `health` worker (1 Hz). Existing acquisition/event threads remain unchanged in ownership. Storage remains synchronous and reports actual mount/write progress instead of pretending to have a worker heartbeat.

## 6. Time boundary

| Clock | Representation | Purpose | Rule |
| --- | --- | --- | --- |
| Monotonic time | 64-bit extended RT-Thread tick, converted to microseconds | durations, timeouts, ordering, data age | Never changes after `time set`. Resolution is 1 ms. |
| UTC | `int64_t utc_unix_seconds` plus `utc_valid` | human/event correlation | Used only when explicitly valid. |

The monotonic provider extends tick wrap and multiplies by 1,000; it does not falsely claim hardware-microsecond precision. IMU FIFO timing stays within acquisition.

Commands and semantics:

- `time status`: validity, UTC, LSE/RTC status, epoch ID, last setting source/offset.
- `time get`: prints UTC only when valid; otherwise prints `invalid`.
- `time set YYYY-MM-DDTHH:MM:SSZ`: accepts UTC between 2000 and 2099, writes RTC then backup-domain magic/version/valid state, and increments `time_epoch_id`.
- `time invalidate`: clears validity only; it does not overwrite the RTC calendar.
- First boot, invalid backup marker, VBAT loss, or LSE failure makes UTC invalid. LSI is not treated as calibrated UTC.

Time-setting audit is a small RAM ring in 07. Persistent audit storage is outside scope.

## 7. SHT4x hardware and environment service

The approved provisional wiring is already recorded in `docs/hardware/sht4x_pinmap.md` and `docs/hardware/board_pinmap.md`.

| SHT4x pin | H743 pin | Board point | Rule |
| --- | --- | --- | --- |
| VDD | 3V3 | P2-41 | Never use P2-42 5V. |
| GND | GND | P2-43 | Common ground. |
| SCL | I2C1 PB8 AF4 | P1-6 | Open drain; 10 kOhm pull-up to 3V3. |
| SDA | I2C1 PB9 AF4 | P1-5 | Open drain; 10 kOhm pull-up to 3V3. |

Place a 100 nF VDD-to-GND capacitor near the module. Initial bus speed is 100 kHz. The driver sends `0xFD`, waits 10 ms, reads six bytes, and validates each two-byte measurement using CRC-8: polynomial `0x31`, initial value `0xFF`, no reflection, xorout zero.

Address is a module property. Boot probes only `0x44`, then `0x45`; exactly one responding address is accepted. Zero or two responders gives a classified unavailable state—never a wide I2C scan.

The service samples once per second and publishes centi-degrees Celsius, milli-percent RH, validity, age, total errors, and last error. A timeout, CRC error, or impossible value never overwrites the last good sample with a fake normal value. Event handling never waits for I2C.

## 8. Health, reset, power, and watchdog

### 8.1 Health state

- `STARTING`: required core providers have not all reported initial status.
- `HEALTHY`: acquisition, event, and storage are ready and making progress.
- `DEGRADED`: recording core is healthy, but UTC is invalid, environment is missing/stale/faulted, or another recoverable auxiliary issue exists.
- `FAULT`: acquisition or event has no progress for 3 seconds; storage cannot mount/write or lacks successful progress for 10 seconds; or sample-pool backpressure rises continuously for 3 seconds.

`POWER_UNAVAILABLE` merely records that PVD is absent; it does not degrade an otherwise healthy recorder. A future active PVD droop is `DEGRADED`. A FAULT requires three consecutive good checks to recover, while fault code, counters, and transition sequence remain visible.

### 8.2 Progress heartbeat and IWDG

A heartbeat means actual work:

- acquisition published a block or consumed valid FIFO data;
- event advanced an event state or drained it;
- storage mounted, recovered, wrote, or committed;
- environment completed one classified polling attempt;
- health completed a provider pass.

Only health may feed IWDG, and only when all required workers have advanced within their deadlines. A periodic timer must never feed IWDG unconditionally. The policy/API is implemented in 07, but physical IWDG starts disabled until board testing proves an approximately 8-second timeout, correct reset classification, and a deliberate stalled-worker reset. WWDG is not used.

### 8.3 Reset/power

At earliest startup, reset-power service captures raw RCC flags, derives one primary cause in this order—BOR/POR, IWDG, WWDG, software, reset pin, other/unknown—then clears raw flags. It exposes both values and never writes Flash.

If PVD is introduced later, its ISR records only a pending droop fact. Any reporting happens in a service thread; the ISR cannot log, wait, or write storage.

## 9. Event context, storage compatibility, and EV02

At trigger acceptance, event assembly makes one non-blocking copy through `health_service_get_snapshot()`. The existing health snapshot is deliberately a health-owned output, not a new global `system_context_t` shared by every module. The copied values are stored in the pending event, so later health, UTC, or SHT changes cannot modify that event. Missing values are represented with validity flags, never a blocking read or deferred rewrite.

### 9.1 EL01 stays compatible; recovery validation stays strict

EL01 block layout, event IDs, commit footer, recovery behavior, and outer CRC remain unchanged. Existing EV01 records remain readable.

`event_log` keeps the existing EV01 integrity checks during recovery: magic, version, header length, event ID, payload length, and inner payload CRC. When EV02 is introduced, the smallest correct change is an additional explicit EV02 validation branch with the same recovery purpose:

- checks EL01 header/footer, bounds, event-ID association, commit state, and outer CRC over payload bytes;
- validates EV01 exactly as before;
- validates EV02 magic, version, header length, event ID, payload length, and inner CRC using its documented offsets;
- rejects unknown payload versions rather than treating them as generic bytes.

This is not a Phase 07 decoupling refactor. It preserves the evidence-integrity judgment made during power-loss recovery. If future duplication becomes material, a small pure `ev01_validate()`/versioned validator can be extracted for event and storage to share; that is explicitly deferred.

### 9.2 EV02 portable payload

New events use little-endian EV02: fixed 128-byte header plus the current 16-byte-per-sample payload. Fields are encoded byte by byte; no packed C struct is stored.

| Offset | Field |
| ---: | --- |
| 0 | `EV02` magic (4 bytes) |
| 4 | `u16 version = 2`; `u16 header_length = 128` |
| 8 | `u32 event_id`; `u64 trigger_monotonic_us` |
| 20 | `i64 utc_unix_seconds`; `u32 time_epoch_id` |
| 32 | sample rate, trigger sequence, pre/post sample counts |
| 48 | subtrigger, event flags, peak and threshold magnitude-squared |
| 60 | payload length and inner payload CRC32 |
| 68 | health state, power state, context-valid flags |
| 72 | raw reset flags, temperature, environment age, humidity |
| 84 | free-log bytes, sample-pool minimum free, reserved zero |
| 92 | last fault, IMU transport/DMA errors, backpressure, storage/export errors |
| 116 | four stack-min-free values (all zero/unavailable in 07) |
| 124 | health transition sequence |

Context-valid bits: UTC valid, environment valid, environment fresh, LSE running, storage ready, power state known, and stack-watermark available. In 07 the last bit is false and stack fields are zero rather than inspecting RT-Thread private memory.

EV01 decode remains supported for existing records. The existing `event_export_debug` module owns EV02 serialization and validation in this phase, avoiding a gratuitous codec-module rename. A new protocol document records EV02 explicitly instead of modifying EV01 silently.

## 10. Diagnostics

MSH commands are presentation-only adapters:

- `time status|get|set|invalidate`
- `health show`
- `env show`
- existing `event` and `log` diagnostics

They format copied public state. Apart from explicit time set/invalidate operations, they do not alter service state or directly touch peripheral registers.

## 12. Acceptance boundaries

Software acceptance requires:

1. Native tests for SHT4x CRC/conversion/error propagation/address selection; time validity and epoch; health transitions and heartbeat gating; frozen health snapshot; EV02 offsets/CRC; EV01 compatibility; and strict EV01/EV02 EL01 recovery validation.
2. Module-boundary checks proving event does not include or call concrete storage implementation, drivers/components do not include `app/`, and no new reverse dependency is added by 07.
3. Firmware build with HAL I2C/RTC/IWDG integration and `git diff --check`.
4. Host tool decoding known EV01 fixtures and EV02 fixtures.

Hardware acceptance remains separate until bench evidence exists:

1. SHT4x voltage/pull-ups/address/CRC and one-hour 1 Hz run.
2. LSE start, VBAT retention, invalid-after-VBAT-loss, and manual time-set persistence.
3. Power-on, reset-pin, software-reset, and IWDG reset-cause classification.
4. IWDG timeout under a deliberately stalled critical worker.
5. Events created with missing SHT4x or invalid UTC show correct EV02 validity flags.

## 13. Approval checkpoint

Implementation may start only after confirming all of these decisions:

1. Reed/door sensing remains entirely outside Phase 07.
2. SHT4x uses PB8/PB9, 3.3V, 10 kOhm pull-ups, 100 kHz, and only probes `0x44`/`0x45`.
3. UTC is explicit-validity data; the device never invents a date.
4. IWDG policy is written but physical watchdog stays disabled by default until hardware verification.
5. EL01 remains compatible and keeps strict EV01/EV02 recovery validation; EV02 uses the fixed header above.

When approved, implementation is one coherent batch in this order: drivers/services, health and its snapshot, EV02 plus strict EL01 recovery branch and host parser, then build/tests/documentation. This document does not itself authorize pin, watchdog, or protocol changes.
