# 高动态运输事件记录器系统设计规格

- 状态：待项目发起人审阅
- 日期：2026-07-13
- 设计目标：形成面向嵌入式软件岗位、以可靠固件为主体并包含可量化端侧 AI 的求职作品集

## 1. 项目目标与边界

项目面向 5～20 kg 精密光电、实验室或高价值仪器运输箱。终端在本地持续监测运输状态，在可疑事件发生时保存事件前后的惯性波形、时间、环境和系统健康信息，到货后通过电脑导出和回放。

开发与演示使用带配重、泡棉和固定结构的工具箱代替真实仪器。项目提供运输风险记录和交付验收辅助，不判断设备是否损坏，不预测寿命，也不宣称达到专业运输认证精度。

项目以嵌入式软件能力为主体：实时采集、RTOS 数据流、可靠存储、Bootloader、OTA、异常恢复和故障注入约占主要工作量；AI 是必须完成、必须与规则基线对比的增强模块。

第一版不包含云平台、GPS、显示屏、音频或视觉、多协议联网、自研 H743 最小系统板和专业锂电池管理 PCB。

## 2. 第一版事件范围

第一版支持以下事件：

1. 明显冲击或安全条件下的软垫跌落：由确定性规则触发，保存低量程与高量程传感器的前后波形。
2. 长时间倾斜或倒置：由低量程 IMU 和持续时间规则判断。
3. 正常手提、推车或车辆颠簸、持续粗暴摇晃：建立规则基线，并由 TinyML 分类器辅助区分。
4. 开箱、温湿度越界、断电、复位、传感器异常、采样丢失和存储错误：作为系统或环境事件记录。

AI 不直接输出“设备损坏”结论，也不取代明显冲击、倒置、温湿度越界和硬件故障规则。

## 3. 硬件架构

### 3.1 主控与开发板

最终主控锁定 STM32H743VIT6：480 MHz Cortex-M7、2 MB 片内 Flash、1 MB RAM。现有 STM32F407VET6 板保留为早期采集验证和性能对照板，不承担最终完整系统。

首选开发板为 WeAct MiniSTM32H743VIT6 或等价板。购买门槛为：

- 板价不超过 200 元；
- 确认为 H743VIT6，不购买 1 MB Flash 的 H743VGT6 或 128 KB 片内 Flash 的 H750VBT6；
- 提供完整原理图；
- 具有可用 SWD、USB、TF 卡接口；
- 具有至少 8 MB SPI NOR 和 8 MB QSPI NOR，或能够以模块方式补齐同等资源。

### 3.2 惯性传感器

采用双量程结构：

- ICM-42688-P 六轴 IMU：负责姿态、低量程振动、运动上下文和 AI 输入；使用 SPI、FIFO、数据就绪中断。
- ADXL375 ±200 g 三轴加速度计：负责普通 IMU 饱和时的冲击证据；使用 SPI、独立片选和中断。

采购分两步：先购买 ICM-42688-P 完成采集闭环；待采集和日志稳定后再购买 ADXL375。若正规 ADXL375 模块明显超过约 120 元，只重新评估高 g 模块，不改变双量程系统边界。

### 3.3 辅助硬件

- SHT40：I²C 温湿度传感器，环境数据不进入第一版 AI。
- RTC：使用 H743 内部 RTC、32.768 kHz LSE 和 VBAT 备用电源；不增加 DS3231。
- 开箱检测：干簧管和磁铁，经 GPIO 中断与软件消抖处理。
- 看门狗与电源监测：使用 H743 IWDG、PVD、BOR 和复位原因寄存器。
- 功耗测量：INA226 仅安装在测试夹具中，不作为产品常驻器件。
- 第一版便携供电：5 V USB 充电宝；必须验证低负载自动关机行为。
- 受保护单节锂电池与 Power-Path 充电模块属于核心闭环完成后的可选增强。

### 3.4 机械安装

桌面驱动联调可临时使用短杜邦线。进入冲击实验前，H743 核心板和传感器必须焊接到统一洞洞板或简单载板，并固定在同一刚性底板上。

两颗惯性传感器靠近底板中心，标明坐标轴，传感器下方不放软泡棉。SHT40 远离 MCU 和稳压器热源并接触箱内空气。整块底板使用四个铜柱固定；充电宝独立使用泡棉和绑带约束。

核心功能和引脚稳定后可制作一块两层载板，用于核心板插座、传感器、CAN 收发器预留、连接器、去耦和测试点。载板不包含自研 H743 最小系统。

## 4. 存储与升级架构

### 4.1 存储职责

- H743 片内 Flash：Bootloader、当前 App 和少量冗余启动状态。
- QSPI NOR：候选固件、旧固件备份、模型 A/B 槽及升级元数据。
- SPI NOR：可靠事件环形日志，由单一存储任务独占。
- TF 卡：开发期数据集、人工导出和归档；不是可信事件主存储。

具体地址、分区大小和擦除单元在取得实际 Flash 型号、App 镜像和模型尺寸后冻结。

### 4.2 事件记录提交

事件日志不依赖通用文件系统。每条记录按以下顺序追加：

1. 写入带“未完成”状态的头部；
2. 分块写入波形和元数据；
3. 写入长度与 CRC32；
4. 最后写入提交标志；
5. 重启时扫描尾部，丢弃未提交记录并恢复写入位置。

索引或超级块保留至少两份带序号和 CRC 的副本。循环空间不足时覆盖最旧的非保护事件；覆盖行为本身写入系统统计。

### 4.3 固件 OTA

采用“外部 QSPI 暂存与备份 + 片内单 App 执行”的复制式升级，不在第一版实现两个不同链接地址的片内 App 直接运行。

应用通过 USB 接收候选固件并写入 QSPI。Bootloader校验包类型、硬件标识、版本、长度和 CRC32，分块复制到片内 App 区并保存升级状态。新固件进入试运行状态，只有通过自检并由 App 确认后才成为有效版本；未确认或连续启动失败时从 QSPI 恢复旧固件。

第一版 CRC32 负责检测传输和存储损坏，不宣称具备升级包来源认证。密码学签名和安全启动不属于最小闭环。

### 4.4 模型 OTA

模型使用独立 A/B 槽。模型清单至少包含模型版本、输入形状、特征版本、量化类型、所需运行时版本、长度和 CRC32。固件只加载兼容且校验通过的模型；失败时继续使用上一有效模型和规则基线。

## 5. 通信与上位机

### 5.1 接口分层

- 主接口：USB CDC 虚拟串口，承载数据导出、参数配置、固件和模型上传。
- 救援接口：独立 UART，承载早期调试、崩溃信息和 Bootloader 救援。
- 计划内增强：核心闭环完成后增加 CAN FD 收发器和 ISO-TP，承载状态、事件摘要、配置和诊断，不传输完整原始波形。

无线网络、MQTT 和 HTTP 不进入第一版。

### 5.2 TERP v1

Transport Event Recorder Protocol 是独立于 USB 和 UART 的二进制应用协议。帧包含 Magic、协议版本、消息类型、标志、序号、Payload 长度、Payload 和 CRC32，统一使用小端序。

协议支持：

- 设备信息、健康状态和版本查询；
- RTC 同步和配置读写；
- 事件列表、事件摘要和分块波形读取；
- 固件与模型的开始、分块、结束和状态查询；
- ACK/NACK、超时重试、重复块识别和断点续传；
- 协议版本与能力协商。

调试文本不得混入 TERP 主字节流。

### 5.3 上位机

上位机使用 Python 3.12、PySide6、PyQtGraph、NumPy、SQLite 和 pytest。先实现无界面的命令行工具与协议测试，再实现 GUI。

上位机至少支持设备状态、时间同步、事件列表、波形回放、规则与 AI 结果对照、固件和模型升级、CSV/JSON/图片导出以及自动化测试报告。

## 6. 固件与 AI 技术栈

- 固件语言：C11。
- RTOS：RT-Thread Standard；不使用 Nano。
- MCU 支持：STM32CubeH7 HAL/LL 与 CMSIS。
- 信号处理：CMSIS-DSP。
- AI 部署：STM32Cube.AI，优先 INT8 模型。
- 构建：SCons + arm-none-eabi-gcc；RT-Thread Studio用于辅助配置和调试，命令行构建作为可复现基线。
- 目标端测试：RT-Thread utest。
- 主机端测试：Python pytest和可移植C模块的原生构建测试。

AI训练使用 Python 3.12、NumPy、SciPy、scikit-learn 和 TensorFlow/Keras。先建立阈值与手工特征基线，再比较小型传统分类器、MLP或轻量1D CNN。最终模型结构由真实数据、交叉验证和MCU资源测量决定，不在硬件启动前固定。

## 7. RTOS任务与数据流

采用流水线和资源单一所有者模型：

1. `sensor_acq`：最高业务优先级，独占惯性传感器 SPI，响应中断并通过 FIFO/DMA 读取数据。
2. `event_engine`：维护预触发缓存，执行规则，切分 AI 窗口并生成事件上下文。
3. `ai_worker`：执行特征提取和模型推理；过载时允许跳过，不阻塞采集。
4. `storage_writer`：独占事件 SPI NOR，写入记录、CRC、提交标志和索引。
5. `protocol_service`：解析 TERP 并向存储、配置和升级模块提交请求。
6. `system_manager`：管理 SHT40、RTC、开箱检测、任务心跳、IWDG、复位原因和运行模式。

OTA初期由维护模式中的系统管理逻辑协调，复杂度增加后才拆分独立任务。

实时路径启动后不使用动态内存。DMA缓冲区32字节对齐并放置在DMA可访问的SRAM，不能放入DTCM；通过MPU非缓存区或明确的D-Cache clean/invalidate规则保证一致性。数据块来自固定内存池，并通过队列转移所有权。AI Tensor Arena静态分配。

事件采集状态依次为 `IDLE`、`PRE_TRIGGER_CAPTURED`、`POST_TRIGGER_CAPTURING` 和 `READY_FOR_STORAGE`。存储提交状态独立为 `UNCOMMITTED`、`FINALIZING` 和 `COMMITTED`。短时间内的重复触发合并到当前采集事件，延长后触发窗口并更新峰值、次数和严重度。只有存储状态到达 `COMMITTED` 的事件才允许对外声称已经持久化。

过载时依次暂停实时GUI流、跳过非关键AI窗口、降低环境写入频率、退化为事件摘要。任何原始数据缺失都必须记录丢失样本数、时间范围和 `DATA_LOSS` 标志。

## 8. 时间、数据和事件一致性

每条事件同时保存RTC UTC时间和单调时间。RTC无效时仍用单调时间保证顺序，并设置 `TIME_INVALID`。时区只在上位机展示层处理。

低量程和高量程传感器第一版不做硬件同步，而是为每个DMA数据块记录同一单调时钟域中的时间戳。同步误差必须通过实验测量；只有误差影响事件解释时才增加外部同步硬件。

采样率、FIFO水位、预后触发长度、规则阈值和事件合并窗口属于实验门控参数。第一阶段先测量总线吞吐、丢帧、RAM和真实波形，再将结果写入配置版本和验收记录，不能只凭经验冻结。

## 9. 异常处理与降级

系统健康状态为 `HEALTHY`、`DEGRADED`、`SAFE_MODE` 和 `BOOT_RECOVERY`。

- 高g传感器失效：进入DEGRADED，继续低量程记录并明确标记。
- 主IMU失效：有限次重试和传感器复位后进入SAFE_MODE。
- SHT40失效：停止环境记录，不影响惯性采集。
- 事件Flash持续写失败：停止声称事件已经持久化，保留诊断和导出能力。
- USB断开：不影响本地采集和存储。
- 模型无效：回退到上一模型和规则。
- 时间无效：保留顺序并显式标记。
- 队列拥塞：按既定降级顺序处理，不能静默覆盖。

所有自动重试都有次数和时间上限。

IWDG只在关键任务按期更新心跳时由系统管理逻辑喂狗。心跳、队列水位、最后错误码和复位原因保存为可恢复健康快照，重启后形成系统事件。

## 10. 验证与故障注入

测试分为四层：

1. PC原生测试：CRC、TERP、记录解析、环形索引、事件状态机和损坏记录恢复。
2. MCU utest：内存池、队列边界、规则、Flash提交、配置与版本兼容。
3. 硬件在环：通过USB自动配置、注入故障、导出结果并生成JSON报告。
4. 长稳和破坏性测试：随机掉电、OTA中断、传感器断线、Flash写满、协议损坏和长时间运行。

Debug固件提供受编译开关控制的故障注入点：SPI错误、丢中断、队列满、Flash指定位置失败、错误CRC、RTC无效、任务心跳停止、OTA指定偏移复位、错误模型版本以及协议块丢失、重复和乱序。Release固件完全关闭这些命令。

最终验证目标为：

- 目标配置下连续采集72小时，所有丢失都能被计数和定位；
- 100次随机掉电后，已提交事件不损坏，未提交尾记录可恢复；
- 30次升级随机中断后，设备始终能够启动旧版本或有效新版本；
- 传感器断开、Flash写满和USB反复连接均产生预期状态和错误记录；
- 协议损坏、重复和乱序测试至少覆盖1000个数据块；
- 报告最大队列深度、任务栈水位、采集时延、推理时延、Flash、RAM和CPU占用。

AI数据按采集批次或运输实验划分训练、验证和测试集，不能将同一连续数据随机切窗后分散到不同集合。保留AI的最低门槛是：在关键风险事件召回率不下降时，相对降低至少20%的误报；未达到时如实报告，规则仍为正式判定路径。

## 11. 延后决策及冻结触发条件

以下项目不是遗漏，而是由实验结果触发的延后决策：

| 决策 | 冻结条件 |
|---|---|
| 开发板具体商家和版本 | 核对价格、原理图、Flash型号和接口后 |
| SPI/QSPI精确分区 | 获得实际芯片擦除粒度、App和模型尺寸后 |
| 采样率、FIFO水位和DMA块大小 | 完成驱动吞吐、丢帧与频谱实验后 |
| 预触发和后触发窗口 | 取得真实动作与冲击波形后 |
| 规则阈值和风险等级 | 形成第一批带标签数据集后 |
| AI特征、窗口和模型结构 | 完成规则基线与候选模型对照后 |
| RTOS具体优先级和栈大小 | 取得最坏时延与栈水位数据后 |
| CAN收发器和报文ID | 核心采集、日志和USB闭环验收后 |
| 锂电池与Power-Path方案 | 完成功耗状态测量并确认续航缺口后 |
| 两层载板 | 所有模块、引脚和接口稳定后 |

## 12. 设计完成判据

本设计只有在以下证据同时存在时才算落地：实物和接线或载板资料、真实波形、事件前后回放、规则与AI对照、资源和时延报告、掉电恢复记录、OTA成功与回滚记录、自动化测试报告、长稳数据、演示视频和可复现README。

项目最终评价以这些证据为依据，不以功能清单或预先承诺的准确率、零丢帧和超低功耗为依据。
